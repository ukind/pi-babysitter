# Solution Analysis: Clear F021-F028 and F008 — commit shape for the fix pass

## Research Question
How should the nine verified fix sites (F021-F028 + F008) be sequenced into commits — what commit shape gives finding-level safety at a verification cost the house can afford?

## Summary
**Problem**: Nine audit findings, all verified at HEAD with exact fix shapes; the open question is commit grouping, ordering, and ledger-stamp placement.
**Recommended**: Hybrid — code findings get one commit each, the two comment-only findings (F027, F008) batch into a final docs commit that also closes the TECH_DEBT_AUDIT ledger. 7 commits.
**Effort**: Low (~1 day including per-commit gates and validation)
**Confidence**: High

## Problem Statement

**Requirements:**
- Each fix lands with its regression fixture (t19b, t15b, t16, t1b fold) in the same commit.
- Three same-commit invariants: F023's alternation group at advisor.ts:133 equals the group at :156; F024's git rm --cached + .gitignore + config.example.json land as one unit; F008's banner pairs with its TECH_DEBT_AUDIT.md row.
- TECH_DEBT_AUDIT.md rows F021-F028 + F008 marked RESOLVED with commit refs within the same series.
- Series stays bisectable; every commit passes test + lint + tsc (CI runs on every push).

**Constraints:**
- Hard: pinned strings are contract (gate reason, t20 detail, t11 message); only the t19b count pin (tests/test.mjs:1127) may change (10 -> 13), exactly once.
- Hard: advisor.ts carries three findings in disjoint regions — no commit may force partial-file staging.
- Soft: house style is 1-4 findings per vertical-slice commit (observed mean 2.0).

**Success criteria:**
- Seven (or fewer) gate-green commits, each naming its finding IDs in the message.
- git log shows one revertable unit per code finding.
- Ledger rows carry fix-commit refs; a fresh clone gets a silently disabled gate (F024 verified end state).

## Solution Options

### Option 1: Per-finding series (8 commits)
**How it works:**
One commit per finding, F021+F022 merged (shared root cause). Each commit carries fix + fixture; the ledger stamps ride each commit or a closer.

**Pros:**
- Maximal revert granularity — one revert unit per finding, including the riskiest fix (the F021+F022 matcher rewrite)
- Fully bisectable to finding level; per-push CI validates exactly one finding in isolation (ci.yml:5-27)

**Cons:**
- 24 gate invocations (8 commits x 3 gates) — 3.4x the hybrid's cost
- 1.13 findings/commit is finer than any house series (observed mean 2.0, min 1)
- Per-commit ledger stamping deviates from house practice (batched in dfa82f8) and hits the hash self-reference snag: a RESOLVED line cannot cite its own commit hash

**Complexity:** Low (~1.5 days)
- Files to create: 1 (config.example.json)
- Files to modify: 10 (gate.mjs, advisor.ts across 3 commits, config.ts, guard.ts, lib.mjs, feedback.mjs, tests/test.mjs across 6 commits, .gitignore, README.md, TECH_DEBT_AUDIT.md)
- Risk level: Low

### Option 2: Hybrid — code per-finding, docs batched (7 commits) — RECOMMENDED
**How it works:**
Six code findings get one commit each (F021+F022, F023, F024, F025, F026, F028). The two comment-only findings (F027 citation reword, F008 banner) batch into a final docs commit that also stamps all nine TECH_DEBT_AUDIT.md rows with the fix commits' refs.

**Pros:**
- Finding-level revert on every code fix — the matcher rewrite stays isolated (evidence: disjoint hunk bands advisor.ts:66-79/:122-161/:315; tests/test.mjs t1b/t15b/t16/t19b)
- Inside house granularity (1-2 findings/commit; single-finding precedent 81a8748, 084b1f8, ad697e5, 43900c2)
- The final docs commit mirrors house's J/dfa82f8 batch stamping AND resolves the hash self-reference snag — the ledger can cite all six fix commits
- 7 gate trios, bisectable, per-push CI validates one finding-group per push

**Cons:**
- F027's revert unit is shared with F008 (trivial: both are comment edits)
- The F025 commit must also carry the config.ts:141/:149-150 prose that turns false ("exact parity with shouldGate", "which stays") — an intra-commit completeness requirement, absorbed by scoping

**Complexity:** Low (~1 day)
- Files to create: 1 (config.example.json)
- Files to modify: 10 (same surface as Option 1, fewer commits)
- Risk level: Low

### Option 3: Layer-split (3 commits)
**How it works:**
Commit 1 = hooks layer (F021+22 matcher, F026 constant); commit 2 = advisor layer (F023 widening + folded citation, F028 operator, F008 banner + its ledger row); commit 3 = config + cleanup (F024 untrack, F025 deletion, F027 reword).

**Pros:**
- Leanest verification: at most 9 gate trios, ~6 CI jobs vs 14 (hybrid) or 24 (per-finding)
- 2/3/3 findings per commit sits inside the house 1-4 range; layer-thematic batching has direct precedent (B config group, G hooks pair 74d3cec, J docs pass)

**Cons:**
- Revert granularity = 3 findings; a matcher failure strands the unrelated F026 in commit 1
- F024's untrack lands last, keeping the personal model tracked longest (exposure time, not functional)
- F008's ledger pairing must be explicitly added to commit 2's file set or it silently drops

**Complexity:** Low (~0.5-1 day)
- Files to create: 1
- Files to modify: 10
- Risk level: Low-Medium (coarser revert units)

### Option 4: Single batch (1 commit)
**How it works:**
All nine fixes, all fixtures, all ledger stamps in one commit.

**Pros:**
- Zero staging complexity; all three invariants trivially satisfied; count pin unambiguous; exactly one gate run

**Cons:**
- Migration blocker: one failing fixture strands eight verified fixes — the only exits are a full revert (losing everything) or an amend that disentangles six test.mjs fixture bands by hand
- 9 findings/commit is 2.25x the house max (dfa82f8's 4, prose-only)
- Not bisectable in any useful sense — CI can only say all-green or some-red

**Complexity:** Low (~0.5 day to write, unbounded to rework)
- Risk level: H
